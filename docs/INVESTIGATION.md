Investigation Notes – CoA Architect Directory Search
Before building anything, I spent some time exploring how the actual search feature works on the Council of Architecture website, since the assignment specifically asks us to understand the system before writing a scraper.
The main directory page is at: https://coa.gov.in/search_arch.php?lang=1&level=1&linkid=&lid=289&lang=1
This isn't a search form by itself — it's more like a menu, with different ways to search: by Name, Registration Number, Year of Registration, State, City, and Pincode. Each of these links to a different search mode using a searCat parameter in the URL (for example, Name search uses searCat=1).
I tried the "Search By Name" option first, using the name of a well-known architect (Balkrishna Vithaldas Doshi) so I could be reasonably sure a real record exists. The search took me to: https://coa.gov.in/search_architectResult.php?lang=1&level=1&linkid=&lid=289
What's interesting here is that the architect's name doesn't show up anywhere in the URL, even though the page clearly used it (it displays "Architect's List Based on [Balkrishna Vithaldas Doshi]" at the top). That suggests the search term is being sent through a POST request rather than a GET request — I confirmed this by checking the Network tab in Chrome DevTools, where the request showed up as a POST to search_architectResult.php.
The results table itself has columns for S.No, Architect Name, Registration Number, Disciplinary Action, Address, Mobile, and Email ID — so these are the fields the system is designed to expose per record.
However, even though the search technically ran, the table showed "No Record(s) Available," followed by a message saying:
"To View further you are required to Login and purchase an Online Directory, 'Click Here' to Proceed!"
This is a clear and important finding. It means the free/public search isn't actually blocked by a CAPTCHA or a technical limitation — it's intentionally gated by the site itself. Earlier, on the homepage, I'd also noticed a note saying unregistered users get 3 free searches per day, and unlimited access requires a paid subscription. Putting both of these together, it's clear that:
The search mechanism works and executes properly.
The response format and fields are consistent and predictable.
But full access to results is deliberately restricted behind a login + paid subscription, not just a soft rate limit.
Because of this, I've scoped my project accordingly: instead of trying to scrape the full live dataset (which the site explicitly restricts), I'm building the full extraction pipeline — database, retry/resume logic, duplicate handling, progress dashboard, CAPTCHA-pause mechanism — and demonstrating it against a small number of records I can legitimately access, along with sample/synthetic data structured to match the real schema, to simulate what a large-scale run would look like.
